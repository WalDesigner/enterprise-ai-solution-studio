# 决策记录

> 文档类型：长期决策与原因
> 状态：当前有效
> 最后复核：2026-08-20（Asia/Shanghai）

## 使用规则

每条决策包含 ID、形成时间、状态、决定、原因和后果。

状态：

- `Active`：当前继续生效。
- `Superseded`：已被新决策替代，并标明替代项。
- `Proposed`：尚需 Product Owner 决定，不能当成已实施事实。

## D-001 — 面试价值优先

- 形成：2026-07
- 状态：Active

**决定**：以 AI 解决方案、售前和实施岗位的面试价值为第一目标。

**原因**：项目的真实成功信号是能够帮助招聘方理解项目负责人如何分析需求、设计
PoC、规划部署和评估价值，而不是代码量或技术炫技。

**后果**：决策顺序固定为 `Interview value > product capability > engineering
elegance > code volume`；无法明确提升目标的复杂能力延后。

## D-002 — 以完整咨询工作流代替单点 Chatbot

- 形成：2026-07
- 状态：Active

**决定**：产品围绕 Dashboard -> Customers -> Analysis -> Solution -> PoC ->
Deployment -> ROI 组织。

**原因**：完整售前与实施路径比单一聊天窗口更能证明企业 AI 解决方案能力。

**后果**：PoC、RAG 和 Agent 是流程中的能力，不是产品唯一定位。

## D-003 — Codex 是 AI Technical Partner

- 形成：2026-07
- 状态：Active

**决定**：Codex 在清晰边界内端到端执行工程任务，而不是等待机械命令。

**原因**：过度详细的 Prompt 会浪费推理能力和时间；Human 更适合保留产品、商业、
安全与外部授权决策。

**后果**：Level 1 / 2 工程改进可以自主完成，Level 3 和外部写操作必须确认。

## D-004 — Demo 阶段不引入数据库、认证和多租户

- 形成：2026-07
- 状态：Active

**决定**：使用脱敏案例数据与浏览器本地持久化完成单用户演示。

**原因**：数据库、认证和多租户会显著增加工程范围，但对当前岗位面试的边际价值低。

**后果**：数据不能跨设备或多人共享；项目不能描述为生产级 SaaS。

## D-005 — 使用服务端 Provider Adapter 和诚实 fallback

- 形成：2026-07
- 状态：Active

**决定**：页面只调用自己的 Route Handler；模型差异、Key、超时、错误和解析由服务端
Adapter 处理，失败时返回明确标识的 Mock fallback。

**原因**：保护密钥、降低 Provider 切换成本，并保证免费服务波动时演示流程仍可继续。

**后果**：不能把 fallback 表述为真实 AI；生产阶段仍需要更强限流、监控和 Secret 管理。

## D-006 — 国内主站与国际备用站双路径

- 形成：2026-07
- 状态：Superseded by D-012

**决定**：CloudBase Run + ModelScope 作为国内主路径，Netlify 作为国际备用。

**原因**：部署平台应根据面试官网络选择，而不是只按开发者熟悉程度选择。

**后果**：必须分别记录两条路径的代码基线和验证证据；不能仅凭两个地址都返回 200
就称它们为同版本镜像。

## D-007 — CloudBase 体验版使用 0-1 实例与自动切流

- 形成：2026-08-19
- 状态：Active

**决定**：CloudBase 保持自动启停、最小实例 `0`、最大实例 `1`、无定时扩缩容；免费
体验版发布使用“发布并自动切换流量”，随后立即验收。

**原因**：历史 3000 资源点主要由 EKS CPU / 内存持续运行耗尽；手动灰度属于付费
标准版能力，低流量面试 Demo 可以接受自动切流风险。

**后果**：存在冷启动；发布前本地门槛必须更严格；失败时优先恢复备用入口。

## D-008 — 真实 AI 只先做 Analysis vertical slice

- 形成：2026-07
- 状态：Active

**决定**：真实 LLM 聚焦 Analysis 方案草案，PoC、Deployment、ROI 保持静态咨询内容。

**原因**：一条完整、可验证的真实纵切面比把不稳定 AI 分散到所有页面更可信。

**后果**：下一条真实 AI 能力优先候选是 ROI Narrative，但不是当前上线阻塞。

## D-009 — Git 和远端写操作必须显式授权

- 形成：2026-07
- 状态：Active

**决定**：commit、push、部署、GitHub visibility / About / topics 和其他外部写操作都
不能从普通实现请求自动推断。

**原因**：保护用户已有工作、远端历史、部署稳定性和账号安全。

**后果**：本地完成不等于自动提交；每种远端动作按当前 Prompt 单独授权。

## D-010 — 按主题维护唯一事实源

- 形成：2026-08-20
- 状态：Active

**决定**：不再把 `MASTER_CONTEXT.md` 称为全项目唯一事实源；按主题拆分：

- 稳定使命 -> `MASTER_CONTEXT.md`
- 当前产品 -> `PROJECT_CONTEXT.md`
- 当前会话 -> `HANDOFF.md`
- 当前部署 -> `DEPLOYMENT_HANDOFF.md`
- 稳定架构 -> `ARCHITECTURE.md`
- 工程流程 -> `ENGINEERING.md`

**原因**：过去多个文件同时维护版本、当前 Sprint 和下一步，导致历史 Handoff 被 Agent
误当成当前指令。

**后果**：其他文档只链接权威入口，不复制会变化的快照。公开切换后的旧文本由当前
Git 历史恢复；切换前材料只从 Private archive 取证，不能重新导入公开仓库。

## D-011 — Netlify 部署源收口

- 形成：2026-08-20
- 状态：Superseded by D-012

**提议**：把 Netlify 重新绑定到规范仓库，而不是长期维护第二个手动同步仓库。

**原因**：当前部署仓库比规范 `main` 少 6 个提交，手动双写已经造成版本漂移。

**结果**：Product Owner 决定不再为低价值备用站维护第二套部署源，改由 D-012 执行。

## D-012 — 国内单主站，退役漂移的 Netlify 镜像

- 形成：2026-08-20
- 状态：Active

**决定**：CloudBase Run + ModelScope 是唯一推荐的简历和面试入口。Netlify 保留为
历史部署实验，不再同步、不再作为回滚目标，也不在公开材料中宣传为备用站。

**原因**：近期目标用户主要位于中国大陆；旧 Netlify 部署源已经产生版本漂移，维护
双仓库的成本高于面试价值。

**后果**：CloudBase 故障时优先回滚上一稳定版本或使用本地 / 录屏材料，不把旧站冒充
同版本产品。未来若重新需要跨区域站点，必须基于规范仓库重新部署并独立验收。

## D-013 — 使用干净公开历史隔离旧工程元数据

- 形成：2026-08-20
- 状态：Active

**决定**：原 GitHub 仓库改名并作为 Private archive 只读保留；公开规范仓库使用原项目
名称，但从经过审查的单一 root snapshot 开始，不导入旧 PR、branch、tag 或 commit。

**原因**：同仓库 force-rewrite 后，旧提交仍可能经 PR refs 或缓存访问；新仓库边界更
容易证明历史 SCF 地址、本机路径和本地作者元数据没有进入公开网络。

**后果**：公开仓库只用于后续可分享开发；旧历史只用于私下审计和恢复，不能把 archive
remote、旧 branch 或 tag 推回公开仓库。当前未添加开源 License，默认不授予复用许可。
